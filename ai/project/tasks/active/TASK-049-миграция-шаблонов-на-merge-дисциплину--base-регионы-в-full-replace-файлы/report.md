# Отчёт TASK-049 — миграция шаблонов на merge-дисциплину

## BLOCKED — требуется решение владельца

Ни один шаблон не тронут. Причина не в сложности, а в том, что **разбор фактических правок
weight опроверг посылку задачи**: `:base`-регионы защитили бы **1 файл из 13**, стоящих под
угрозой. Продолжать без решения владельца — значит потратить работу по 22 шаблонам на почти
нулевой эффект.

Плюс по ходу найден отдельный дефект с воспроизведением: **[BUG-032](../../bug-reports/032-t115-missing-enum-parse-helper-parity-gap.md)**
(High) — в t115 нет `enum_parse.dart`, regen сущности с enum-полем ломает компиляцию.

## Что выяснено

### Граница `:base` в существующих merge-шаблонах

Из девяти шаблонов с `:base` (3 типа × 3 сущности) конвенция читается однозначно, пример
`category_dao.dart`: заголовки (`// manifest:`, `ignore_for_file`) — **выше** региона, а
**закрывающая скобка класса — ниже** конца региона. То есть кастом дописывается методом
внутрь класса, после машинных методов.

Механика понятна и переносима. Проблема не в ней.

### Разбор 13 файлов weight: что за правки на самом деле

Классификация по наличию удалений в диффе (удаления = тронут существующий машинный код):

| Категория | Файлов | Спасёт ли `:base` |
| --- | ---: | --- |
| аддитивная правка (только `+`) | **1** | **да** |
| правка внутри машинного кода | **12** | **нет** |

Единственная аддитивная — `weighing_repository_impl.dart` (`3dcf6003`):

```dart
+  @override
+  int get syncPriority => 10; // после справочников
```

Ровно тот случай, под который `:base` и сделан: член класса, дописанный после машинных
методов. Два файла из 271 такого вида.

Остальные 12 — правки **внутри** сгенерированного кода. Примеры:

`weighing_state_providers.dart` (`ac464554`, subscription-guard) — тела сгенерированных
методов обёрнуты в try/catch, изменена аннотация:

```dart
-@riverpod
+@Riverpod(keepAlive: true)
-    await ref.read(createWeighingUseCaseProvider)!(weighing);
+    try {
+      await ref.read(createWeighingUseCaseProvider)!(weighing);
+      ...
+    } on SubscriptionInactiveException catch (e) { ... }
```

`weighing_entity_extension.dart` (`cb5c3751`) — заменены выражения в машинных
mapping-строках плюс добавлен локальный хелпер:

```dart
-        status: serverpod.WeighingStatus.values.byName(status),
+        status: _tryParseEnum(serverpod.WeighingStatus.values, status) ?? ...open,
```

`driver`/`vehicle`/`contractor_state_providers` (`bc6a7a1f`) — переписаны тела трёх
мутирующих методов (`+9/-12` в каждом).

**Это ровно тот класс, который ADR-0007 §5 вынес за скобки:**

> Правка тела сгенерённого метода не сохраняется **ни одной** маркерной схемой. Это вопрос
> точек расширения (callback/strategy/wrapper/subclass), отдельное API-решение — не делать
> вид, что маркеры его закрывают.

Задача TASK-049 как сформулирована делает именно то, от чего ADR предостерегает.

### Уточнение вердиктов TASK-048: часть правок регенерация улучшит

Шесть из 12 — это локальные версии фиксов, которые **уже есть в шаблоне**:

- `ref.mounted`-гарды в `driver`/`vehicle`/`contractor`/`weighing_state_providers` —
  в шаблоне присутствуют (TASK-032, 3 вхождения в `category_state_providers.dart`).
  Regen выдаст канонический вариант → правку терять **не жалко**;
- `tryParseEnum` в `weighing_entity_extension` — emit-сторона в генераторе есть (TASK-027),
  но **хелпера в t115 нет** → BUG-032, regen ломает сборку.

Остаются **6 действительно ценных** правок, и все они внутри машинного кода:
subscription-banner в `weighing_state_providers` / `weighing_remote_data_source` /
`weighing_data_providers` (`ac464554`) и точечные изменения в трёх `*_extension` (`ccde34ab`,
`113aec87`).

## Почему это блокер, а не «сделаю как написано»

`:base` в целевых 22 шаблонах даст:

- **плюс:** молчаливая потеря превратится в громкий конфликт, а дописанные **члены**
  (не тела) будут выживать без конфликта. Это реальная ценность — но на замеренных данных
  weight она равна одному файлу;
- **минус:** 22 шаблона × (правка + `create-project` + `verify`) + дизайн-решение по границе
  для каждого типа. Для `*_state_providers` граница вообще неочевидна: там два top-level
  объявления, класс закрывается в середине файла, и «оставить закрывающую скобку снаружи»
  как в dao не получается.

Решение о том, каким путём закрывать правку тел, — архитектурное, в task.md и ADR его нет,
и оно **задевает stack-lock** (ADR-0007 §6: «новые callback API — задевают, требуют явного
approval»).

## Варианты (решает владелец)

1. **Сузить TASK-049 до типов, где кастом дописывают членами** — `repository_impl`,
   `usecases`, `*_data_source`. Дешевле, честнее по эффекту, закрывает подтверждённый случай
   `syncPriority`. `*_state_providers` и `*_extension` не трогать — там правят тела.
2. **Сначала BUG-032**, отдельной мелкой задачей (перенести `enum_parse.dart` в t115 +
   инъекция импорта + enum-поле в фикстуру, чтобы `verify` перестал быть слепым). Это
   High-дефект с воспроизведением, дешёвый фикс, и он снимает один из шести «ценных» файлов.
3. **Дискуссия по точкам расширения** (ADR-0007 §5) — как сохранять правку тела: hook-методы,
   `@protected`-переопределение в подклассе, callback в конструкторе. Затрагивает stack-lock,
   поэтому через `discuss.py` + ADR, а не решением исполнителя.
4. **Сделать как написано** — все 22 шаблона. Даёт общее улучшение дисциплины на будущее,
   но на текущем weight спасёт один файл. Если цель «на будущее, а не под weight» — вариант
   рабочий, только надо это назвать вслух.

Моя рекомендация: **2 → 1 → 3**. BUG-032 сначала (дешево, High, с красным тестом), потом
суженный TASK-049 (эффект подтверждён), потом дискуссия про тела — она самая дорогая и без
неё 6 ценных правок weight всё равно придётся портировать руками.

## Что сделано в этой ветке

- разбор 13 файлов, классификация правок (аддитивные / внутри машинного кода);
- воспроизведение BUG-032: `errors=0 → errors=5`, точный текст `undefined_method`;
- bug-report [032](../../bug-reports/032-t115-missing-enum-parse-helper-parity-gap.md);
- шаблон t115 **не тронут** (`git status` в нём — только предсуществующая правка

## Отдельная находка про шаблон t115

В t115 **не закоммичена** правка `task_tag_map_table.dart` с маркером
`:driftTableImports` — это template-сторона TASK-039 (merged PR #49). Значит в свежем клоне
t115 фикса cross-feature drift-таблицы нет. Требует решения владельца: коммитить в t115 или
это намеренно отложено.
